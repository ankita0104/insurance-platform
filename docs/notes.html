I spent 4.5 yrs at the analysis end (discrepancy analysis). A Data Engineer owns the pipeline in the middle. Two projects prove it: earthquake (real API source) and insurance (daily CSV file drops — the realistic insurance pattern).

My edge: data quality is the #1 blocker to AI adoption. My discrepancy background = building trustworthy data, reframed as engineering.

Lesson 1 — Ingestion done

Load a source into a raw table. Extract → Load → Query.

Key steps

  • Project + venv + git (isolated tools, tracked history).
  • Read the source. Insurance: a daily claims CSV; DuckDB reads it natively.
  • Load into a raw_claims table; query to prove it worked.

The core line (DuckDB native CSV read)

CREATE OR REPLACE TABLE raw_claims AS
SELECT * FROM read_csv_auto('landing/claims_2026-08-22.csv')
Why CSV, not API: insurance data arrives as batch file drops from source systems, not web APIs. This is the realistic ingestion pattern.
Interview-ready summary

I built an ingestion pipeline that lands a daily claims CSV export into a raw_claims table using DuckDB's native CSV reader, then reports basic metrics. This mirrors real insurance ingestion, where claims arrive as batch file drops rather than APIs.

Lesson 2 — Idempotency & Incremental Loads done

Make re-runs safe (no duplicates) and load only new records.

Key ideas

ConceptMeaning
IdempotentRunning twice = same result as once. Safe to re-run.
IncrementalAdd only new records; don't wipe & reload; preserve history.
Audit columnloaded_at = when each row arrived.

The two mechanisms

CREATE TABLE IF NOT EXISTS raw_claims (
    claim_id VARCHAR PRIMARY KEY,   -- duplicates impossible
    ... , loaded_at TIMESTAMP )

INSERT INTO raw_claims
SELECT *, now() FROM read_csv_auto('...')
ON CONFLICT (claim_id) DO NOTHING   -- skip already-seen

The proof

Load day 1 → +150. Load day 1 again → +0 (idempotent). Load day 2 → +40, skip 5 (incremental). Total 190.

Insurance stakes: a non-idempotent loader could double-count a claim → double-pay a payout or misstate reserves to regulators. This prevents the exact discrepancy I used to hunt manually.
Interview-ready summary

I made the claims loader idempotent and incremental: a primary key on claim_id plus ON CONFLICT DO NOTHING means re-running a file never creates duplicate claims, and daily files add only new claims while preserving history. I also stamp a loaded_at audit timestamp. In insurance this directly prevents double-counting payouts and reserve misstatements.

Lesson 3 — dbt done

Transformations as tested, documented SQL. dbt does the "T" in ELT.

The core mechanic

A model = one .sql file with one SELECT. dbt wraps it in CREATE TABLE <filename> AS (...). Rules: no CREATE TABLE, no trailing semicolon.

-- stg_claims.sql → builds a table called stg_claims
select claim_id, policy_id, claim_amount, status,
    case when claim_amount < 1000 then 'small'
         when claim_amount < 10000 then 'medium'
         when claim_amount < 30000 then 'large'
         else 'catastrophic' end as severity_band
from raw_claims

Two links (build the dependency graph / DAG)

{{ source(...) }}a raw table dbt did NOT build (input)
{{ ref(...) }}another dbt model dbt DID build (dependency)

Config files

dbt_project.ymlproject settings — the "what". Names project + which profile.
profiles.ymlthe connection — the "where". DuckDB path / Snowflake account.

The 3 names must match: project name = models: key, and profile: = profiles.yml key. Kept separate so the same SQL runs on DuckDB or Snowflake unchanged.

Commands

dbt runbuild models
dbt testrun data-quality tests
dbt buildrun + test together, in order
dbt compileshow the SQL without running (target/ folder)

Tests (in schema.yml)

columns:
  - name: claim_id
    data_tests: [ not_null, unique ]
  - name: status
    data_tests:
      - accepted_values: { values: ['approved','pending','denied'] }
Interview-ready summary

My dbt project has a tested staging layer over claims and policies — not_null and unique on the keys to enforce identity and prevent duplicate claims, and accepted_values on status and derived bands. A model is a SELECT with no trailing semicolon; ref() and source() build the dependency graph so dbt runs everything in order. Every dbt build transforms and validates in one step.

Lesson 4 — Data Quality & Observability done

My signature. Watching data HEALTH over time, beyond build-time tests.

Testing vs Observability

Testing (L3)Observability (L4)
Does data break my rules?Is data healthy over time?
Catches KNOWN issues (a locked door)Catches UNKNOWN issues (a security camera)

The 5 pillars — pattern: METRIC → EXPECTATION → STATUS

PillarQuestionCheck
FreshnessIs data recent?age of newest row > 1 day = stale
VolumeNormal row count?a day < 50% of average = low
SchemaRight columns/types?expected column+type pairs exist
DistributionSane values?0 nulls, 0 out-of-range
LineageWhere from / what breaks?dbt's dependency graph
The judgment layer (senior skill): a flag is a QUESTION, not a verdict. Automated checks find candidates; human judgment decides which are real vs explainable (e.g. a partial first day of data). That separation is what makes alerts trustworthy — exactly my discrepancy-analysis instinct.
Interview-ready summary

I built a data observability suite covering the five pillars — freshness, volume, schema, distribution as SQL checks, plus lineage via dbt. Each check computes a metric, compares it to an expectation, and emits an OK/WARNING status. My differentiator: I don't just detect anomalies, I judge which are real problems versus explainable artifacts — which is what makes alerts trustworthy.

Lesson 5 — Dimensional Modeling in progress

Kimball star schema: organize data for analysis. A named JD requirement.

Facts vs Dimensions

FactDimension
Ismeasurable events (numbers)descriptive context (who/what/when)
Testyou SUM/AVG ityou GROUP BY / filter on it
Insurancea claim (claim_amount)policy, date, claim_type

The star schema

          dim_date
             │
dim_claim_type ─ FCT_CLAIMS ─ dim_policy
             │
        (dim_state)

Fact in the center (metric + foreign keys), dimensions radiate out. Every question = join fact to dimension(s), group by dim attributes, aggregate the metric.

dbt layering (staging → marts)

models/staging/  stg_claims, stg_policies   -- cleaned sources
models/marts/    dim_policy, dim_claim_type, dim_date, fct_claims

Marts built from staging via ref(). A generated dimension uses SELECT DISTINCT (e.g. dim_claim_type from the distinct claim types).

Interview-ready summary

Dimensional modeling, from Kimball, organizes data into fact tables — measurable events like claims with their amounts — and dimension tables — descriptive context like policy, date, and claim type. Arranged as a star schema it makes analytical queries simple and consistent: join the fact to dimensions and aggregate. It's the standard structure for warehouse reporting and BI.

SQL toolbox practised

Four tools worth having automatic.

FILTER — conditional aggregation

count(*) FILTER (WHERE status = 'denied')  -- count only matching rows

OVER () — window functions (aggregate without collapsing rows)

avg(claim_amount) OVER ()                       -- overall avg on every row
avg(claim_amount) OVER (PARTITION BY claim_type) -- avg per group

INTERVAL — date/time math

WHERE claim_date > (SELECT max(claim_date) FROM claims) - INTERVAL 30 DAY

information_schema — the DB's catalog of itself

SELECT column_name, data_type FROM information_schema.columns
WHERE table_name = 'stg_claims'
Portability: DuckDB lets you reuse SELECT aliases in a CASE; Snowflake/Postgres do NOT — repeat the full expression for production SQL.
Interview-ready summary

I use conditional aggregation with FILTER, window functions to compare each row to its peer group, interval date math, and schema introspection via information_schema — the same operations I'd use for claims monitoring and fraud signals.

Gotchas I hit (and fixed)

  • DuckDB single-writer lock: only one process can open the DB. Close any D prompt (.quit) before running dbt/Python. Use duckdb -readonly for querying.
  • No semicolon in dbt models: a model is wrapped in CREATE TABLE (...); a trailing ; breaks it. Semicolons are for the CLI, not models.
  • Triple quotes """: multi-line SQL string in Python. Missing them makes Python try to run SQL as code.
  • Indentation: if __name__ == "__main__": must be flush-left (top level), not indented inside a function.
  • Derived column placement: a CASE ... END AS x lives INSIDE the SELECT list, not after FROM.
  • CASE order: conditions check top→bottom, first match wins.
